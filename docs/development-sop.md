# TimeCalc 开发全流程标准作业程序（SOP）

> 版本：v0.2
>
> 状态：待评审，M1 启动前生效
>
> 适用阶段：Windows MVP（M1 ~ M5）

## 1. 目的与适用范围

本文档定义 TimeCalc 从调研、需求确认、里程碑规划、架构设计、实现、测试、代码审查到验收发布的端到端流程，并把每个阶段的进入条件、输出物和退出条件固化为可检查的门禁（Gate），减少返工与范围膨胀。

### 1.1 文档分工

| 文档 | 角色 | 回答的问题 |
|---|---|---|
| [产品需求文档](requirements.md) | What | 做什么、为什么、验收标准、P0/P1/P2、里程碑退出条件 |
| [开源项目借鉴清单](open-source-references.md) | Reference | 参考谁、许可证边界、借鉴原则与记录要求 |
| [开发检查清单](checklists.md) | Check | 每个功能与里程碑怎么逐项算通过 |
| [贡献指南](../CONTRIBUTING.md) | Who | 谁参与、Issue/PR 流程、分支与提交约定 |
| 本文档 | How | 每个阶段怎么做、做什么检查才能进入下一阶段 |

### 1.2 适用对象

- 项目开发者：按本文档执行各里程碑与每个 Pull Request 的流程。
- AI 编码代理：本文档作为开发本项目时的行为约束与自查清单。

### 1.3 适用时点

- 每个里程碑（M1~M5）启动前与结束时。
- 每个 Pull Request 创建前与合并前。
- 引入新第三方依赖、新增或变更功能范围、调整技术栈时。

### 1.4 优先级规则

- 本 SOP 不改变 [产品需求文档](requirements.md) 的功能优先级；若两者冲突，以 PRD 为准，并按 §6 维护规则更新本文档。
- 里程碑范围由 PRD 的 P0/P1/P2 划分锁定；未经 PRD 变更流程，不得在 MVP 内扩大范围。

## 2. 核心原则速览

所有阶段的行为决策都应回到以下产品原则（详见 PRD §2.3）：

1. **本地优先**：无账号、离线可用全部非 AI 核心功能；不提前建设同步框架。
2. **今天优先**：首页先回答"今天做什么"，再展示统计与长期计划。
3. **计划可修正**：延期和调整是正常流程，不以惩罚性文案制造焦虑。
4. **AI 可选且可撤销**：AI 只生成草稿，用户确认后才写入正式计划。
5. **数据归用户所有**：支持导出、备份和恢复，不将用户内容默认上传。

实现层面的四条硬约束：

- 数据事实保存在本地数据库；规则放在可单元测试的纯 Dart service；Widget 只负责展示和发送用户意图。
- 任务完成、延期、跨多表删除和 AI 草稿批量应用必须使用数据库事务；备份恢复必须通过事务或经校验的临时库替换原子生效，禁止半条写入。
- 时间戳用 UTC 存储，计划日期按本地日历日期单独存储，避免时区漂移。
- 引入第三方代码前先过许可证检查，并记录借鉴决策。

## 3. 阶段流程

每个阶段按「输入 → 步骤 → 输出 → 质量门禁」执行。S1~S2 属于启动与规划，S3~S6 属于开发循环，S7 属于里程碑收口；S0 仅在引入或更新第三方依赖、复制外部代码，或现有调研不足以支持决策时执行。对同一个里程碑，S1~S2 至少执行一次，S3~S6 可针对多个 PR 循环执行，S7 在里程碑结束时执行；只有计划生成可分发构建时才执行 S7 中的发布步骤。

### S0 调研与借鉴

**输入**：[开源项目借鉴清单](open-source-references.md) 中目标能力的推荐项目；需要引入的第三方依赖清单。

**触发条件**：引入或升级第三方依赖、复制或改写外部代码、采用新的外部实现方案，或已有记录超过 90 天且将据此作出重要技术决策。未触发时，在里程碑记录中注明「S0 不适用」及原因。

**步骤**

1. 先阅读 [开源项目借鉴清单](open-source-references.md) 中对应能力的首选参考，明确要借鉴的是「问题拆解、交互流程、数据边界、测试策略」，而不是复制实现。
2. 对每个候选依赖/参考项目核对以下信息，并在借鉴决策记录表（附录 C）中登记：
   - 项目当前维护状态、最后发布版本与最近活跃度。
   - Windows 平台支持情况（针对 Flutter 桌面能力）。
   - 实际使用版本仓库中的 `LICENSE`、`NOTICE` 和依赖条款，不能只依据 GitHub 搜索结果。
   - 已知问题、替代方案。
3. 按许可证边界决定使用方式（详见清单 §6）：

   | 许可证 | 默认处理 |
   |---|---|
   | MIT / BSD-3-Clause | 可在满足版权和许可证声明要求后使用或修改代码 |
   | Apache-2.0 | 可使用，保留许可证、版权与 NOTICE，关注专利条款 |
   | GPL-3.0 / AGPL-3.0 | 仅作研究参考，不复制代码；确需使用先评估项目整体许可证 |
   | 未声明许可证 | 不复制、不修改、不分发代码，只阅读公开页面了解思路 |

4. 引用开源项目时，不复制项目名称、品牌资产、插图、截图、文案或具有明显辨识度的视觉设计。
5. AI 功能相关调研只借鉴流程（输入收集、草稿预览、人工调整），不借用其他项目的提示词；TimeCalc 的提示词须围绕自己的目标、截止日、每日可用时长和不可用日期设计，并建立测试样例和版本号。

**输出**

- 已填写的借鉴决策记录表（附录 C）。
- 引入依赖的 PR 中的「项目/版本/用途/许可证/替代方案」记录。

**质量门禁**

- 所有新依赖均已在记录表中登记许可证与维护状态。
- 不存在未声明许可证、GPL/AGPL 代码被复制进 MVP 的情况。
- MVP 不引入清单中标记为「低优先级 / 待需求确认」的组件（如 flutter_gantt）。

### S1 需求与范围确认

**输入**：功能需求、缺陷报告、产品建议。

**步骤**

1. 将每个功能点映射到 [产品需求文档](requirements.md) 的具体 FR 条目与 P 级；无法映射的需求属于范围变更。
2. 对照 PRD §4.3「明确不做」清单；新需求若与之冲突，需先修改 PRD。
3. 范围变更流程：先在 PRD 中更新对应 FR 与验收标准，通过评审后再进入实现，禁止「先写代码、后补文档」。
4. 明确每个功能的数据模型影响：涉及 Goal/Subject/Milestone/Task/ChecklistItem/RecurrenceTemplate/AIDraft/Settings 中哪些实体，是否触及 schema 变更。
5. 明确异常状态（参照 PRD §8 状态表）：无数据、过载、逾期、AI 未配置、AI 失败、数据库异常时分别呈现什么。

**输出**

- 功能 × FR × P 级映射表（可并入 PR 描述或 Issue）。
- 更新后的 PRD（仅当发生范围变更时）。

**质量门禁**

- 每个待开发功能都能找到对应的 FR 编号与 P 级。
- 无与「明确不做」清单冲突的项被纳入 MVP。
- 涉及 schema 变更的功能已标注需要同步编写 migration 与 migration 测试。

### S2 里程碑规划与排期

**输入**：PRD §12 的里程碑 M1~M5 与退出条件；S1 产出的功能映射表。

**步骤**

1. 以 PRD 定义的里程碑为唯一时间盒，为当前里程碑拆分工作项（可按 FR 拆）并排出先后顺序。
2. 为每个工作项标注其退出证据（测试、演示、演练结果），确保里程碑退出条件可度量。
3. 单里程碑内不膨胀范围：P1 能力按 PRD 的建议在 P0 稳定并验证后再逐个进入迭代，P1 不应在缺少用户验证时同时全部启动。
4. 与 PRD §12 里程碑的建议映射对齐（正式范围以 PRD 为准）：

   | 里程碑 | 建议覆盖 | 关键退出条件 |
   |---|---|---|
   | M1 数据与目标闭环 | 目标/科目/任务 CRUD、本地数据库与 migration | 重启持久化、删除确认、关键边界测试通过 |
   | M2 每日执行闭环 | 今天页、日历、完成/延期、负载计算 | "查看今日任务 → 完成/延期 → 查看更新后进度"可连续完成 |
   | M3 进度与数据保障 | 基础统计、热力图、手动备份恢复、托盘与窗口恢复 | 备份恢复演练通过；10,000 条任务性能达基线 |
   | M4 MVP 发布候选 | 无障碍、异常状态、安装包、回归测试 | P0 验收全通过；无阻断级数据丢失或启动失败 |
   | M5 首个增强迭代 | 按验证结果选择：AI 草稿、重复任务、检查项、燃尽趋势、自动备份、悬浮窗 | 由 MVP 验证结论决定，不一次性全启动 |

5. 为高风险项预留返工时间：日期/时区、Windows 多屏与 DPI、备份恢复、批量写入原子性。

**输出**

- 当前里程碑的工作项清单、顺序与退出证据定义。

**质量门禁**

- 里程碑范围未超出 PRD 对应阶段的 P0/P1 边界。
- 每个工作项都有可验证的退出证据。

### S3 架构与设计

**输入**：S1 功能映射、S2 工作项、PRD §9 数据模型与 §11 技术约束。

**步骤**

1. **数据层（drift）**：按 [清单 §3.4 Drift](open-source-references.md#34-drift) 参考官方文档与示例设计表定义、关联与查询。
   - 每次 schema 变更必须设计 migration 策略与失败恢复方案，并配套 migration 测试；升级前生成可验证备份或快照，失败时不得继续打开部分迁移的数据。
   - 统计尽量由可验证的查询产生，避免在多个状态对象中维护重复计数。
   - Windows 下确认 SQLite FFI 初始化、连接生命周期与并发规则。
2. **状态层（Riverpod）**：按 [清单 §3.5 Riverpod](open-source-references.md#35-riverpod) 组织。
   - Provider 按功能模块组织，避免全局万能状态对象；Repository、时钟、网络状态、AI Provider 均通过注入提供。
   - 用 `AsyncValue` 表达加载、空数据、失败与重试；考虑页面离开后的生命周期与资源释放。
3. **业务规则层**：排程、负载计算、倒计时等规则放在可单元测试的纯 Dart service 中，不依赖数据库或 UI。
4. **日期与时区**：遵循 PRD §9 —— UTC 存储时间戳，本地日历日期单独存储；设计覆盖跨日、跨年、DST 的测试样例。
5. **Windows 平台层**：托盘、窗口位置/DPI/多屏恢复、快捷键、Credential Manager/DPAPI 访问收敛到平台隔离层，业务代码不直接调用 Windows API。
6. **模块划分**：按功能领域（目标、任务、计划、进度、设置）划分目录；不照搬大型项目的整体复杂度（参考清单 §4.2 关于 AppFlowy 的边界说明）。

**输出**

- 涉及 schema 变更时：表结构变更说明、migration 方案、升级前备份/快照与失败恢复策略。
- 涉及新功能时：数据流与状态归属说明（哪个 Provider、哪个 service、哪个事务）。

**质量门禁**

- 数据事实归属数据库、规则归属纯 Dart service、UI 不直接执行 SQL 或调用 AI。
- 每个 schema 变更都有 migration 与 migration 测试计划。
- 没有为单个功能引入超出 MVP 范围的架构设施（如同步框架）。

### S4 实现

**输入**：S3 设计产出；[贡献指南](../CONTRIBUTING.md) 的流程约定。

**步骤**

1. 从 `main` 创建短期分支，命名 `feat/<feature>` 或 `fix/<defect>`；小文档修正可直接提交 PR。
2. 保持提交范围单一，提交信息使用清晰的祈使句（如 "Add task completion transaction"）。
3. 遵守数据完整性硬规则：
   - 任务完成、任务延期、跨多表删除和 AI 草稿批量应用使用数据库事务（NFR-2）。
   - 禁止半条写入：AI 草稿应用失败时不写入部分计划（FR-6.5）。
   - 备份恢复先在临时库完成格式、版本、约束和关键计数校验，再通过事务合并或原子替换正式库；任何失败都保留原数据库（NFR-2、FR-9）。
   - 预估时长仅接受 1～1440 分钟整数，非法输入有明确错误提示（FR-3 验收）。
   - 重复任务采用「模板 + 实例」模型，仅预生成未来 30 天实例并滚动生成（FR-4.3、PRD §11）。
   - 延期操作保留任务内容、归属与预估时长，并记录原计划日期（FR-3 验收）。
4. 隐私基线（NFR-3）：日志不得记录 API Key、完整请求正文或用户隐私内容；API Key 只经 Credential Manager/DPAPI 存取。
5. 新增用户可见功能时，同步更新 PRD 或相关文档。

**输出**

- 通过本地静态检查（`flutter analyze`）与既有测试的代码变更。

**质量门禁**

- 分支命名、提交粒度与提交信息符合约定。
- 涉及日期/时区、数据库迁移、跨多表写入或备份恢复的改动已包含针对性测试（不放入"后续补测试"）。
- 同一 PR 内无无关重构。

### S5 测试

**输入**：S4 代码变更；PRD 的验收标准与非功能需求。

**步骤**

1. 分层测试：
   - 纯 Dart 单元测试：排程、负载、倒计时等 service 规则。
   - DAO/Repository 测试：使用内存数据库（drift 支持的内存库），覆盖查询与事务。
   - Widget 测试：关键用户流程（创建目标、完成任务、延期、备份恢复入口）。
2. 按变更范围执行必测项；标记为「适用」的项目缺一不可，未触及的项目在 PR 中记为「不适用」并说明原因：
   - 日期与时区：涉及日期、时钟或排程时，覆盖跨日、跨年、DST；截止日"今天/昨天/未来"显示正确（FR-1.2）。
   - 数据库迁移：涉及 schema 变更时，覆盖升级成功、升级失败后原库仍可用，以及备份/快照恢复（NFR-2）。
   - 多表写入原子性：涉及完成、延期、目标删除、批量导入或 AI 草稿应用时，覆盖中途失败不产生半写入数据。
   - AI 错误路径：交付或修改 FR-6 时，覆盖非法 JSON、超时或字段缺失不落库。
   - 备份恢复：交付或修改 FR-9 时，覆盖损坏文件、版本不兼容、校验失败与生效中断，确认原数据库不变。
   - 边界输入：涉及任务时长时，覆盖预估时长 1/1440/非法值（FR-3 验收）。
   - 性能基线：M3 起或影响关键查询/渲染路径时，覆盖 10,000 条任务下月历切换 ≤ 500 ms（NFR-1）。
3. 测试与实现同步提交，不允许"实现先行、测试后补"。

**输出**

- 与变更配套的测试代码及测试运行记录（`flutter test`）。

**质量门禁**

- 所有适用必测项均已覆盖，不适用项已说明原因；关键用户流程有自动化测试。
- 测试运行无失败，且没有为了通过测试而绕过业务规则。

### S6 代码审查

**输入**：S4/S5 产出的 PR。

**步骤**

1. 按 [贡献指南](../CONTRIBUTING.md) 提交 PR，说明变更内容、验证方式和已知限制。
2. 审查人按以下清单检查：
   - **数据一致性**：事务覆盖完成/延期/跨多表删除/AI 批量应用；备份恢复原子生效；无重复计数状态；统计来自查询。
   - **范围**：是否夹带无关重构；是否超出本 PR 的 FR 范围。
   - **许可证合规**：新依赖/复制代码是否满足许可证声明要求并记录（S0 记录表）。
   - **隐私**：日志、上报内容不含 API Key、完整请求正文或用户内容（NFR-3）。
   - **可访问性**：状态不只依赖颜色；控件有可读名称；核心流程可键盘操作（NFR-4）。
   - **性能**：符合 NFR-1 基线；没有明显可避免的重绘或全表扫描。
   - **测试**：必测项已覆盖；migration 测试存在。
3. 审查意见通过 PR 评论记录；阻塞问题未解决前不合并。

**输出**

- 合并到 `main` 的 PR（含审查记录）。

**质量门禁**

- 审查清单全部通过。
- 无未记录的第三方代码引入；无隐私数据进入日志或上报。

### S7 里程碑验收与按需发布

**输入**：里程碑结束时的代码与测试结果；PRD §12 退出条件。

**步骤**

1. 逐项核对当前里程碑的退出条件（附录 D 里程碑门禁 Checklist），记录证据。
2. M3 起执行数据演练：备份 → 修改数据 → 恢复 → 校验数据一致，确认「覆盖恢复前自动创建安全副本」生效（FR-9.3）。
3. 仅当本里程碑计划生成可分发构建时，对照 [清单 §3.3 LocalSend](open-source-references.md#33-localsend) 与 §3.1 Mhabit 的发布实践，管理版本号、变更日志、签名、安装包与 Release 资产；MVP 阶段只维护 Windows 发布渠道。
4. 回归测试：确认本里程碑未破坏既有 P0 流程。
5. 若发布，记录版本号、变更内容、验证方式和已知限制；若不发布，在验收记录中写明结果和下一里程碑输入。

**输出**

- 里程碑验收记录（退出条件逐项打勾）。
- 发布版本与变更日志（仅计划发布时）。

**质量门禁**

## 5. 异常与回滚

### 5.1 运行期异常

| 异常 | 处理方式 | 依据 |
|---|---|---|
| AI 未配置或网络不可用 | 展示原因与手动排程入口，而非仅将按钮置灰 | FR-6.8 |
| AI 请求失败 | 保留用户输入，给出重试与手动编辑入口；不落库 | PRD §8 状态表 |
| AI 返回非法结构 | 解析失败即丢弃草稿，正式任务库不产生脏数据 | FR-6.3/6.5 |
| 数据库异常 | 停止继续写入，提示从备份恢复或导出诊断信息 | PRD §8 状态表、NFR-2 |
| 备份路径不可写（自动备份） | 通知用户，不静默失败 | FR-9.4 |

### 5.2 发布与数据回滚

- 版本回退：保留上一版本安装包；回退以用户数据不丢失为前提，禁止用降级覆盖更高 schema 版本的数据库。
- schema 升级采用向前迁移：升级前创建并验证备份或快照；迁移失败时关闭新库、保留失败诊断并恢复迁移前副本，禁止用旧版本应用直接打开或覆盖更高 schema 数据库。
- 覆盖恢复（FR-9.3）前自动创建当前数据安全副本，作为用户操作级回滚点。

## 6. 维护规则

在以下时点更新本 SOP：

- TimeCalc 的 MVP 范围或技术栈发生变化（SOP 与 PRD 一起评审）。
- 某个阶段流程暴露明显问题（如门禁漏检导致缺陷流出）。
- 新增里程碑或引入新的发布渠道。
- 借鉴清单或 PRD 发生会改变流程的更新。

修订时优先保持章节编号稳定；结构确需调整时同步修复所有交叉引用。版本号递增，并在本节记录变更摘要。

### v0.2 修订摘要

- 将 S0 改为触发式调研，避免每个里程碑重复执行无关调研。
- 区分里程碑验收与对外发布，发布资产只在计划分发构建时要求。
- 补齐跨多表删除、迁移失败和备份恢复的原子性及失败恢复要求。
- 将测试门禁改为按变更范围判定适用性，避免未选 P1 功能阻塞 P0 开发。
